ผลรีวิว

โครงหลักตรงกับ spec แต่ยังไม่ผ่าน Definition of Done สำหรับ production เครื่องมือ schema, procedure, Query Store และ diagnostics มีครบเป็นส่วนใหญ่ ขณะที่ SELECT/estimated plan ถูกปิดโดยค่าเริ่มต้น การควบคุมข้อมูลลับยังมีช่องทางรั่ว และยังไม่มีผลทดสอบกับ SQL Server จริงหรือบัญชีที่ล็อกสิทธิ์แล้ว

คำว่า “read-only” มีสองชั้น: โค้ดตั้งใจส่งเฉพาะคำสั่งอ่าน และบัญชี SQL ต้องถูกจำกัดสิทธิ์จริงในระบบปลายทาง รายงานนี้ตรวจโค้ดและ SQL setup script ได้ แต่ยังตรวจสิทธิ์จริงของ login ที่จะ deploy ไม่ได้

ที่มาและขอบเขต

เกณฑ์หลักคือ spec SQL Server Review MCP ที่ผู้ใช้แนบมา โดยเฉพาะ §5–6 (security/account), §7–14 (tools), §15–18 (limits/redaction/audit/errors), §19–20 (capability/tests) และ §24 (Definition of Done) จุดประสงค์คือให้ AI reviewer ไล่หลักฐานจาก endpoint ไปจนถึง SQL Server โดยไม่แก้ state ของระบบ

ผมตรวจ การลงทะเบียน tool, ชั้น query, SQL guard, account script, tool handlers, config, README และ tests ปัจจุบัน รายงานนี้เป็นการตรวจแบบ static พร้อม build/unit tests; ไม่ได้ยิงคำสั่งกับ production หรือ SQL Server ตัวอย่าง

ระบบทำงานอย่างไร

AI client→MCP stdio→Zod validation→tool handler→mssql pool→SQL Server

index.ts โหลด environment และต่อ stdio transport; server.ts ลงทะเบียน tool และห่อผลเป็น JSON พร้อม audit; capabilities.ts probe feature ตอน startup; query.ts ผูก parameter, timeout และ stream ผลที่มี row cap

สำหรับ SQL ที่ผู้เรียกส่งมาเอง มี SQL guard ปฏิเสธ DML/DDL และหลาย statement, row cap, timeout และ redaction ของชื่อคอลัมน์ ก่อนตอบ MCP ทั้งสอง tool นี้ต้องตั้ง SQLSERVER_ENABLE_AD_HOC_SQL=true จึงปรากฏในรายการ tool ตาม server.ts และ .env.example บัญชี SQL ใน create-review-user.sql เป็นขอบเขตสิทธิ์หลัก; script ให้ VIEW DEFINITION/VIEW DATABASE STATE และ DENY write แต่ SELECT บนข้อมูลและ SHOWPLAN ต้อง grant แบบเลือกเอง

มีข้อจำกัดตามธรรมชาติของ interface: MCP นี้ดูหลักฐานฝั่งฐานข้อมูลได้ แต่ไม่สามารถวัด Browser Network, frontend หรือ backend โดยตรง การเชื่อมจุดเหล่านั้นต้องใช้โค้ด application และข้อมูลจาก browser/API ที่ AI reviewer มีจากแหล่งอื่น

ข้อค้นพบที่มีผลจริง

P1ข้อมูลลับยังออกทางผล tool ได้

get_active_expensive_queries คืน LEFT(t.text, 2000) เป็น commandText ตรง ๆ หาก session อื่นรัน SQL ที่มี literal token/password ข้อมูลนั้นจะถูกส่งถึง MCP client แม้ audit log ไม่เก็บ SQL แล้ว อีกทางหนึ่ง execute_select redact ตาม ชื่อคอลัมน์ผลลัพธ์ เท่านั้น: SELECT password AS value หลบ pattern ได้เมื่อ account มี SELECT บนตารางนั้น ขัดกับ spec §16 ที่ห้ามเผย obvious credential fields

ทิศทางแก้: ตัด command text ออกจาก active requests หรือคืน fingerprint/ข้อความที่ scrub literal อย่างเชื่อถือได้ และจำกัด SELECT บนข้อมูลจริงอย่างเข้มงวด; redaction จาก alias ไม่ใช่ขอบเขตความปลอดภัยที่พอจะรับรอง production

หลักฐาน: src/tools/diagnostics.ts:249–255; src/tools/query.ts:33; src/security/redaction.ts:18–27; spec §16

P1Node รุ่นที่ประกาศว่ารองรับรันคำสั่ง start ไม่ได้

package.json ระบุ node >=20.6 แต่ start/dev ใช้ --env-file-if-exists ซึ่ง เอกสาร Node.js CLI ระบุว่าเพิ่มใน v22.9.0 ดังนั้นเครื่องที่ใช้ Node 20 LTS ตามเงื่อนไข package จะเริ่ม server ผ่าน npm scripts ไม่สำเร็จ

ทิศทางแก้: เปลี่ยน minimum version เป็นรุ่นที่รองรับ flag หรือใช้วิธีโหลด env ที่ทำงานบน Node 20; ตรวจ README และ extension launch command ให้ตรงกัน

หลักฐาน: package.json:12–18; Node.js CLI reference

P2Query Store ถูกมองว่าใช้งานได้ทั้งที่ actual state เป็น OFF/ERROR

capabilities.ts probe ว่ามองเห็น actual_state ได้หรือไม่ แล้วให้ queryStore=true โดยไม่ตรวจค่า state หาก Query Store ปิดหรืออยู่ใน ERROR tool ด้าน Query Store จะผ่าน gate แต่ได้ผลว่างหรือ error แบบ DATABASE_ERROR แทน QUERY_STORE_DISABLED ตาม spec §18–19 ทั้งที่ get_database_info มีการตรวจ actual state อยู่แล้ว

ทิศทางแก้: อ่าน actual_state_desc ใน startup probe แล้วกำหนด capability จาก READ_WRITE/READ_ONLY/READ_CAPTURE_SECONDARY และบันทึกเหตุผลจริง

หลักฐาน: src/db/capabilities.ts:25–29; src/tools/database-info.ts:41–45; Microsoft Query Store catalog reference

P2Probe บางตัวไม่ได้พิสูจน์ permission ที่อ้าง

viewDefinition ถือว่าผ่านเมื่อ query OBJECT_DEFINITION(...) ทำงาน แม้ค่าที่ได้เป็น NULL เพราะไม่มีสิทธิ์หรือไม่มี procedure ส่วน viewServerState ใช้การอ่าน sys.dm_exec_sessions ซึ่งไม่ยืนยันว่าอ่าน DMV/index usage ที่ tool ต้องการได้จริง ผลคือ capability flag และ usageStatsAvailable อาจบอกว่าพร้อมทั้งที่ข้อมูลจริงไม่มา

ทิศทางแก้: ใช้ HAS_PERMS_BY_NAME กับสิทธิ์ที่ต้องการหรือ probe DMV เดียวกับ tool และแยกสถานะ “ไม่มี object ให้ทดสอบ” ออกจาก “มี permission”

หลักฐาน: src/db/capabilities.ts:40–49; src/tools/indexes.ts:71–117; spec §19

P2Tool บางตัวไม่มี limit แม้ผลโตได้

get_blocking_summary คืนทุกแถวจาก waiting tasks และ get_table_stats คืนทุก stats object ของ table โดยไม่ใช้ TOP หรือ maxRows ใน runQuery หาก server มีการรอจำนวนมากหรือ table มี stats มาก ผล MCP และหน่วยความจำจะโตโดยไม่มี cap ขัดกับ spec §15

ทิศทางแก้: เพิ่ม input limit/default, ใช้ TOP แบบ parameterized และส่ง maxRows ไปชั้น query; บอก truncated เมื่อมีรายการเกิน cap

หลักฐาน: src/tools/diagnostics.ts:72–106, 183–215; src/db/query.ts:49–87; spec §15

P2ยังพิสูจน์ SQL boundary และ driver behavior ไม่ได้

unit tests 50 รายการผ่าน แต่ integration tests 3 รายการถูก skip และ test สิทธิ์บัญชีใน live.test.ts ลอง UPDATE sys.objects ซึ่งไม่ใช่ application table และจะล้มเหลวแม้ login บางชนิดมี write สิทธิ์บน application table ดังนั้นยังพิสูจน์ข้อ §24(11) “account independently prevents writes” ไม่ได้ อีกทั้ง estimated plan/stream cancel/Query Store SQL ยังไม่เคยรันกับ SQL Server จริงในรอบนี้

ทิศทางแก้: ใช้ disposable SQL Server พร้อม application table fixture และล็อก account ตาม script, ทดสอบ SELECT/plan/Query Store/row limit รวมถึง write attempt โดยตรงบน fixture

หลักฐาน: tests/integration/live.test.ts:7–43; tests/tools/stream-limit.test.ts:27–38; spec §20, §24

เทียบกับ spec แบบเป็นหมวด

หมวด specสถานะหลักฐานและเงื่อนไข
§2 เทคโนโลยี / stdioตรงTypeScript, official SDK, mssql, zod; index.ts ต่อ StdioServerTransport; server.ts แยกจาก transport
§5–6 read-only accountต้องพิสูจน์จริงSQL script มี DENY DML/DDL และไม่ grant broad role; สิทธิ์จริงของ deploy account ยังไม่ถูกทดสอบบน application table
§7–14 toolsมีครบแบบมี gate20 ชื่อ; execute_select และ get_estimated_plan ไม่ register โดยค่าเริ่มต้น; optional tools เพิ่มครบ 6 ชื่อ
§15 limits / timeoutบางส่วนgeneric SELECT stream/cancel; Query Store history มี cap; blocking/table stats และบาง metadata responses ยังไม่มี cap
§16 redactionยังเสี่ยงredact ตาม output column name ใน execute_select; active commandText และ alias ยังเผยข้อความได้
§17–18 audit / errorsส่วนใหญ่ตรงaudit JSON ลง stderr, SQL fingerprint; driver errors เปลี่ยนเป็นข้อความทั่วไป; audit ปิดได้ด้วย env

§20 / §24 tests & DoDยังไม่ครบ50 unit tests ผ่าน; 3 integration tests skip; ไม่ได้พิสูจน์พฤติกรรมกับ SQL Server จริง

ตัวอย่างการใช้เพื่อรีวิว endpoint

สมมติ browser แจ้งว่า GET /api/customers?keyword=abc ใช้ 4.2 วินาที reviewer ต้องดู route/controller/repository จากโค้ดแอปเอง แล้วใช้ MCP ตรวจฐานข้อมูลตามลำดับนี้:

  1. ใช้ describe_procedure/get_procedure_definition หรือดู SQL ใน repository เพื่อรู้ query ที่ backend ส่ง
  2. ใช้ query_store_top_queries หา query/plan ที่สัมพันธ์กับ SQL นั้น แล้ว query_store_query ดู duration/reads และ runtimeHistory ตามช่วงเวลา
  3. เปิด ad-hoc gate เมื่อ account/permissions ถูกตรวจแล้ว และใช้ get_estimated_plan ตรวจ scan, sort, lookup หรือ conversion ของ SELECT เดียวกัน
  4. ใช้ describe_table, get_indexes, get_table_stats ยืนยันโครงสร้าง/index/statistics; ใช้ waits/IO/blocking เป็นหลักฐานเสริม

ข้อสรุปที่ปลอดภัยคือ “Query Store แสดงอ่าน 1.8M pages และ estimated plan มี clustered scan บน dbo.Customers; ควรทบทวน predicate/index แล้ว benchmark workload เดิม” ยังสรุปว่า DB เป็นสาเหตุทั้งหมดของ 4.2 วินาทีไม่ได้หากไม่มี timing ของ frontend/backend และ actual workload ที่สัมพันธ์กัน

การตรวจสอบและข้อจำกัดของผลรีวิว

ตรวจ build ด้วย npm run build ผ่าน และ npm test ผ่าน 50 tests; integration tests 3 tests ถูก skip ตาม RUN_INTEGRATION_TESTS รอบนี้ไม่ได้ตรวจ startup MCP กับ client จริง, SQL Server network/Query Store จริง, SHOWPLAN permission หรือสิทธิ์บัญชีใน production

ลำดับที่ควรทำก่อนรับรอง: แก้ data exposure และ Node version, ทำ capability probe ให้ตรง state/permission, ใส่ cap ให้ tool ที่ขาด, จากนั้นตั้ง disposable SQL Server พร้อม locked-down account แล้วรัน end-to-end tests. หลังผ่านจึงเปิด ad-hoc gate ใน environment ที่ต้องใช้
